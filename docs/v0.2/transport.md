# Structured-output transport for v0.2

The canonical documents are JSON-LD. Some model structured-output adapters reject property names beginning with `@`, including `@context`, `@type` and `@vocab`. v0.2 keeps the v0.1 approach: a generated transport representation with provider-safe aliases.

## Alias mapping

| Transport property | Canonical JSON-LD property |
|---|---|
| `jsonldContext` | `@context` |
| `jsonldContext.vocab` | `@context.@vocab` |
| `jsonldType` | `@type` |

All other properties and values are identical in both forms. The `id` and `type` aliases inside the context are ordinary property names whose *values* are `@id` and `@type`, so they need no transport rewriting and every entity keeps its identifier and type in both forms.

## Documents

| Canonical | Transport |
|---|---|
| `schemas/career-profile.v0.2.schema.json` | `schemas/career-profile.transport.v0.2.schema.json` |
| `schemas/opportunity-intent.v0.2.schema.json` | `schemas/opportunity-intent.transport.v0.2.schema.json` |

## Source of truth

The canonical schemas are authoritative. Transport schemas are generated by `scripts/build-transport-schema.mjs`, which also generates the v0.1 pair.

```bash
npm run build:transport-schema
npm run check
```

The check fails if any checked-in transport schema is stale, or if any property beginning with `@` survives into a transport schema or transport example.

## Shared definitions

A single-file schema cannot use a cross-file `$ref` and stay usable as a structured-output schema, so the career profile and opportunity intent schemas each carry their own copy of the definitions they share: the context, identifiers, validity, source documents and locators, provenance, claims, taxonomy mappings, disclosure, ambiguity and warnings.

The build script compares every definition name that appears in both v0.2 schemas and fails if the copies have drifted apart. When editing a shared definition, edit both files and re-run the check.

## Conversion

`scripts/convert-profile.mjs` and `src/v0.2/transport.ts` implement the same lossless mapping, and the converter is document-agnostic: it works for both v0.2 documents and for v0.1.

```bash
node scripts/convert-profile.mjs --to-transport profile.jsonld transport.json
node scripts/convert-profile.mjs --to-canonical transport.json profile.jsonld
```

Conversion does not validate. Validate against the input schema before conversion and against the output schema after it.

## Storage rule

The transport form is an ingestion and generation boundary only. Persist and exchange the canonical JSON-LD representation unless a specific integration contract requires the transport form.
